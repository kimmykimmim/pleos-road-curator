## 1. 먼저 내리는 판단

**현재 앱이 모든 평가 기준을 충분히 충족했다고 판단하지 않는다.**

이유는 앱의 방향이 공모전과 어긋나서가 아니다. **차량 특화 경험과 구현 근거는 있지만, 사업성 설명과 제출물의 최신 상태가 그 수준을 따라오지 못한다.** 핵심 차량 연동도 개별 기능 및 정차 시연의 근거와 실제 내비 입력으로 끝까지 이어지는 검증을 구분해야 한다.

| 공식 평가 항목 | 현재 판단 | 가장 강한 근거 | 남은 약점 |
|---|---|---|---|
| 차량 특화성 | 방향은 부합, 입증은 부분 충족 | 내비 ETA와 GPS, 차의 진행 방향, 정차 상태, 차량 오디오와 연결 | ETA → 질문 → 통과 → 해설 → 답변의 전체 연결 증거 부족. 스마트폰 대비 우위 설명에 과장 있음 |
| 창의성 | 차별화 요소 있음, 독창성 입증은 부분 충족 | 6~8세 관심사 질문, 평가하지 않는 반응, 가족 기억, 장소의 인물이 되는 놀이 | 위치 기반 오디오 자체는 기존 서비스에도 존재. 사용자 문제를 실제로 확인한 자료 없음 |
| 기술 활용성 | 활용 기준에는 부합, 완성도 검증은 부분 충족 | NaviHelper·Vehicle·TTS·STT가 핵심 흐름에 사용됨. 앱·서명 APK·검사·영상 존재 | 실제 내비 모드의 음성 참여와 방향·정차 연동 등 전체 경로 미검증 |
| 사업성 | **현재 가장 부족** | 가족이라는 타깃과 지역 확대 방향은 있음 | 초기 고객 범위, 확보 경로, 예상 MAU 산식, 재이용 지표·가설, 콘텐츠 공급 운영 계획 부족 |
| 개발 산출물 가산점 | 자료는 상당 부분 준비, 제출 확정은 미확인 | 소스, release APK, 기존 영상과 추가 역사 영상 | 신규 영상 미추적, README·기획서 구버전, 현재 비공개 저장소의 심사 접근 방식 확정 필요 |

공식 페이지는 네 항목의 **세부 배점과 합격선을 공개하지 않는다.** 위의 “부분 충족”은 검토자의 근거 기반 판단이다. 이를 임의의 100점 점수나 “4개 중 3개 통과”로 바꾸지 않는다. 2차 PT의 상세 기준도 별도 공지 대상이므로 이 보고서의 기준은 공개된 1차 평가 기준과 영상의 개발·PT 안내다. [공식 심사·시상](https://appdevchallenge.auto-hmg.io/guide/judging-awards)

## 2. 영상을 어떻게 검토했는가

- 제공된 한국어 수동 자막 전체 645개 구간을 시작부터 종료까지 읽었다. 자동 번역만 보고 요약하지 않았다.
- 영상의 심사 장표가 나오는 약 12:30과 기술 설명 약 32:08은 브라우저에서 실제 화면과 자막을 대조했다.
- 따라서 아래는 **전체 자막 검토와 주요 화면 대조**의 결과다. 모든 프레임을 42분간 연속 시청했다고 표현하지 않는다.
- 영상 전체 파일 내려받기는 접근 오류가 있었으나, 자막 전체 확보 및 브라우저의 해당 영상 재생·장표 확인은 가능했다.
- 영상 이후 달라질 수 있는 접수 규정은 검토 시점의 공식 홈페이지와 추가 공지로 확인했다.
- 앱 근거는 현재 소스, 문서, APK, 저장된 검사 결과, 앞선 직접 실행·역사 시연 촬영 결과다. 이번에 앱 기능 전체를 새로 재검사한 것은 아니다.

## 3. 영상 당시 안내와 현재 규정의 차이

### 3.1 비공개 저장소: 심사용 계정 초대 안내는 현재 기준이 아님

영상 [11:00](https://www.youtube.com/watch?v=na6tSJ44pWc&t=660s)에는 심사용 계정을 초대하라는 안내가 있다. 그러나 현재 추가 공지는 초대를 요구하지 않으며, 제출 커밋을 특정한 뒤 정해진 기간 공개하거나 공개가 어렵다면 소스·APK 압축본의 내려받기 경로를 제공하는 방식을 안내한다. 현재 저장소는 GitHub 조회 결과 `PRIVATE`다. **현재 비공개인 것 자체가 탈락 사유라는 뜻은 아니지만, 최종 심사 접근 경로를 정해야 한다.**

현재 공지의 일정은 11월 15일 23:59 접수 마감, 비공개 저장소의 공개 전환은 11월 16일까지, 공개 유지는 11월 23일까지다. 공개가 어려운 경우 압축본 경로는 접수 마감 전에 제출하도록 안내한다. 접수 메일에는 최종 커밋 번호가 필요하다. [공식 추가 공지](https://appdevchallenge.auto-hmg.io/notice/c0a1a000-2026-4923-8000-000000000007)

우리 `docs/발표자료.html`에는 아직 “심사 계정 아이디 문의, Collaborator 추가 필요”가 남아 있다. 그대로 실행할 체크리스트로 쓰면 안 된다. 이 검토에서는 저장소 공개나 이메일 발송을 수행하지 않았다.

### 3.2 실제 차량이 없어도 심사 가능

영상 [21:05](https://www.youtube.com/watch?v=na6tSJ44pWc&t=1265s)에서 실차 시연을 지원하지 않고 에뮬레이터로 검증한다고 답한다. 현재 공지도 실제 차량이 필요하지 않다고 안내한다. **실차가 없다는 사실을 필수요건 미충족으로 판단하면 안 된다.**

다만 앱 화면에 데모 신호를 넣은 것과, 실제 SDK의 신호 변화가 앱을 움직인 것은 다른 근거다. 남은 과제는 무조건 실차 확보가 아니라 에뮬레이터·Virtual Console에서 핵심 연동을 입증하는 것이다. 에뮬레이터 버전과 화면 규격은 README에 명시해야 한다. [현재 심사 환경 안내](https://appdevchallenge.auto-hmg.io/notice/c0a1a000-2026-4923-8000-000000000007)

### 3.3 AI·외부 API는 허용되지만 필수는 아님

[20:28의 AI 활용 답변](https://www.youtube.com/watch?v=na6tSJ44pWc&t=1228s)은 기획·개발 보조를 허용하면서 참가자 본인의 기술 설명 능력을 요구한다. [37:49의 답변](https://www.youtube.com/watch?v=na6tSJ44pWc&t=2269s)은 외부 API·네트워크를 허용한다. 우리 앱이 외부 AI를 호출하지 않는 것은 평가 위반이 아니며, AI를 쓰기 위해 기능을 바꿀 필요도 없다.

영상 약 25:56에는 미공개 SDK 제공 예정 취지의 발언도 있다. 이 발언만으로 특정 경로 좌표 API가 이미 제공된다고 단정하지 않는다. 현재 사용 가능한 문서·버전·호출 결과를 기준으로 가능한 범위를 설명한다.

### 3.4 숏폼과 개발 시연을 구분

본상 가산점용 시연은 화면 녹화도 인정된다. 숏폼은 별도 이벤트다. 현재의 약 50초 모음은 가로에 가까운 편집 영상이며, 길이가 1분 이내라는 이유만으로 숏폼 참여 요건을 충족하는 것은 아니다. 세로 형식·게시·해시태그·링크 등의 별도 조건을 확인해야 한다. 숏폼 불참을 본상 평가의 결함으로 볼 필요는 없다. [공식 숏폼 안내](https://appdevchallenge.auto-hmg.io/guide/shortform)

## 4. 항목별 상세 판단

### 4.1 차량 특화성 — 차량에서 더 유용해지는 이유는 있으나 표현과 검증을 보강해야 함

**현재 강점**

- 가는 길의 장소를 주제로 삼아 이동 자체를 경험에 사용한다. 임의의 교육 콘텐츠 재생과 구별된다.
- 목적지·경유지별 남은 시간으로 질문 시점을 정하고, GPS 접근·통과와 다른 방식으로 구분한다.
- 연속 위치로 진행 방향을 구해 장소가 어느 쪽 창에 있는지 안내하는 로직이 있다.
- Vehicle의 기어·브레이크, 차량 UX 제한, 오디오 우선순위, 전경 서비스가 화면·음성 경험을 바꾼다.
- 후석 아이가 중앙 화면에 손이 닿지 않는 문제를 음성 참여로 풀려는 구조다.

**미흡하거나 입증되지 않은 부분**

- 실제 내비 입력의 약 5분 전 질문부터 통과·해설까지 전체 연결은 아직 미검증이다. 새 역사 영상도 이를 증명하지는 않는다.
- 방향·정차 판단이 단위 함수에서 맞는 것과 SDK의 실제 상태 변화에 반응하는 것은 구분해야 한다.
- 현재 `BackSeat.shouldListen()`과 `usable()`은 제한 상태 및 비전경 상태에서 듣기를 열지 않는다. 따라서 실제 이동 중·다른 화면에서도 항상 대화한다고 홍보할 근거는 없다. 제한을 준수하는 청취 모드와 참여 가능한 상태를 구별해 설명해야 한다.
- `docs/기획서.md`와 발표자료의 “휴대폰은 진행 방향을 모른다 / 할 수 없는 일” 주장은 과하다. 우리 코드도 진행 방향을 연속 위치로 계산하며, 모바일 GPS 오디오 투어도 존재한다. 차량 내비·차량 상태·공용 오디오와의 통합이 더 정확한 우위다.

**추천 설명**

> 아이가 이미 타고 있는 차량의 경로·정차 상태·음성 환경에 맞춰, 지나가는 장소를 질문과 가족 대화의 계기로 바꿉니다.

근거: `CuratorNaviSource.kt`, `domain/LiveNavigation.kt`, `domain/WindowDirection.kt`, `VehicleStillness.kt`, `domain/Stillness.kt`, `CuratorDriveService.kt`, `domain/BackSeat.kt`. 비교 참고: [GuideAlong의 모바일 GPS 오디오 동작 설명](https://guidealong.com/how-it-works/).

### 4.2 창의성 — 차별화 가능한 조합은 있지만 “기존에 없던 GPS 이야기 앱”은 아님

**현재 강점**

- 6~8세라는 이용자와 보호자라는 설정 주체가 분명하다.
- 과학·역사·예술 등의 질문 선택과 후속 대화, 사실과 상상 구분, 부정 평가를 피하는 응답이 구현되어 있다.
- 숭례문의 문지기, 광화문의 안내자, 청진옥의 이야기 전달자 등 장소별 놀이가 있다.
- 보호자가 직접 적은 가족 기억과 가족 장소를 같은 흐름에 연결한다.

**미흡한 부분**

- 위치에 맞춰 이야기를 들려주는 것 자체는 새롭지 않다. Autio와 GuideAlong은 공식 설명에서 위치 기반 오디오를 제공한다. 이들 서비스의 모든 기능을 조사한 것은 아니므로 특정 어린이 기능이 없다고 단정하지 않는다. 다만 “GPS 이야기는 우리가 처음”이라는 주장은 방어하기 어렵다. [Autio](https://autio.com/), [GuideAlong](https://guidealong.com/how-it-works/)
- 부모와 아이가 실제로 어떤 상황에서 불편을 겪고, 기존 대안이 왜 부족한지 확인한 인터뷰·관찰 자료는 찾지 못했다.
- “창밖을 더 본다”, “가족 대화가 늘어난다”, “멀미를 줄인다”는 효과를 실제 사용자 검증 결과처럼 제시하면 안 된다. 현재는 의도 또는 검증할 가설이다.

**차별화의 중심**

“관광지 설명 자동 재생”보다 **아이 취향에 맞는 질문 → 아이 생각을 존중하는 대화 → 실제 풍경 관찰 → 가족의 기억·놀이**를 보여 주는 것이 낫다. 새로운 역사 영상은 이 폭을 보여 주는 데 유용하지만, 그 자체가 독창성이나 효과를 입증하는 자료는 아니다.

### 4.3 기술 활용성 — SDK 사용 자체는 충족, 실제 연결 증거는 더 필요

| 기술 | 핵심 경험과의 연결 | 현재 판단 |

FusedLocation을 추가로 사용하지 않는다고 감점 사유라고 단정할 수 없다. 영상은 SDK 나열이나 개수가 아니라 필요한 기술이 핵심 경험에 쓰이는지를 강조한다. 개발 단계의 매니페스트 권한 선언과 App Market 배포 승인도 다른 단계다. [영상 32:02](https://www.youtube.com/watch?v=na6tSJ44pWc&t=1922s), [공식 개발 환경](https://appdevchallenge.auto-hmg.io/guide/development)

**이번에 확인한 객관적 근거**

- 현재 소스와 제출용 release APK의 버전은 모두 0.30.0 / 32다.
- `aapt dump badging`으로 패키지·버전·최소 API 28을 확인했다.
- 제출용 APK는 `apksigner verify` 종료 코드 0으로 서명 검증을 통과했다. 이번 점검에서 release APK를 새로 설치한 것은 아니다.
- 기존 `testDebugUnitTest` XML은 총 357개, 실패 0, 오류 0이다. 이번에 검사를 재실행한 것은 아니며, 이전 보고의 346개에서 갱신된 결과를 직접 확인했다.
- 앞선 작업에서 이 버전의 debug 빌드를 Pleos 에뮬레이터에 설치해 역사 경로를 직접 실행·촬영했다.

단위 검사 357개를 통과했다는 이유만으로 내비·위치·오디오·마이크의 통합 동작까지 검증됐다고 표현하지 않는다.

### 4.4 사업성 — 타깃은 보이지만 확보·유지·확대의 구체성이 부족

공식 기준은 타깃뿐 아니라 이용자 확보, 예상 MAU, Retention Rate, 확대 계획을 예시로 든다. 매출이 이미 발생해야 한다는 뜻은 아니다. 출시 전이라면 **가정이 명시된 예상 규모와 검증 계획**을 제시할 수 있다. [영상 심사 장표 12:30](https://www.youtube.com/watch?v=na6tSJ44pWc&t=750s), [공식 사업성 기준](https://appdevchallenge.auto-hmg.io/guide/judging-awards)

| 사업성 요소 | 현재 상태 | 필요한 보완 |
|---|---|---|
| 이용자와 구매·설정 주체 | 아이와 보호자가 정의됨 | 최초 고객을 지원 지역·차량 환경까지 좁혀 명시 |
| 문제의 빈도·강도 | 등하원·주말 이동을 제시 | 부모 관찰·인터뷰 등 실제 근거 |
| 사용자 확보 | 제조사·지자체 연계 방향만 있음 | 첫 사용자를 어디서 만나고 무엇으로 설치를 유도할지 |
| 예상 MAU | 산식·수치 근거 없음 | 도달 가능한 지원 차량 가족 × 노출률 × 설치율 × 월 활성률. 각 값은 가정·출처·검증 방법 표시 |
| 지속 이용 | 반복 질문과 가족 기억을 근거로 듦 | 재이용의 지표 정의와 목표 가설, 콘텐츠 소진 대응 |
| 서비스 확대 | 지자체·장소 데이터 확장 방향 있음 | 장소당 작성·검수·번역·사진 권리 확인 비용, 업데이트 주체와 주기 |
| 수익·비용 | 명시적 모델과 운영비 근거 부족 | 유료 콘텐츠, 제휴 등 후보 중 무엇을 검증할지. 계약이 없는 협력을 확정 사업처럼 쓰지 않기 |

**초기 고객의 현실적인 정의 예시:** “서울의 지원 장소를 자주 지나는 경로에서 6~8세 아이를 태우는 Pleos 이용 가족.” 전국 모든 어린이 동승 가족을 현재 고객으로 잡으면 서울 6곳이라는 공급 범위와 맞지 않는다.

**지표를 쓸 때 주의할 점:** 사용자는 아이·보호자·가족·차량 중 어느 단위인지 먼저 정한다. MAU는 월 1회 이상 의미 있는 여행을 시작한 가족/차량 수 등으로 정의하고, 7일 재이용률과 장면 완료율은 서로 다른 지표로 둔다. 아직 측정하지 않은 숫자를 실적으로 적지 않는다. 현재 앱에 이를 측정하는 분석 기능이 있다는 의미도 아니다.

기획서의 “가족 기록을 다른 앱으로 가져갈 수 없어 떠나기 어렵다”는 설명은 유지율 증거가 아니다. 이탈 장벽보다 아이가 다시 하고 싶어 하는 이유와 보호자가 느끼는 편의를 설명하는 편이 낫다.

## 7. 우선순위: 새 기능보다 먼저 할 것

### 1차 접수 마감 전 우선

1. **사업성 한 페이지 보강:** 초기 고객, 첫 확보 경로, 예상 MAU 산식과 가정, 재이용 지표, 지역 확대 운영 방법을 적는다. 실제 실적과 목표를 구분한다.
2. **기획서·README 최신화:** 0.30.0 / 32, 357개 검사, 실제 Pleos 환경, 사진·언어·자동 듣기 범위, 남은 검증을 서로 맞춘다.
3. **심사 접근 경로 확정:** 비공개 저장소 처리 방식과 최종 커밋, APK 경로, 영상 경로, 서명본을 실제 제출 묶음 기준으로 확인한다. 이 보고서 작성 자체로 공개·발송·푸시하지 않는다.
4. **새 시연 자료 포함 여부 결정:** 약 50초 모음과 역사 원본 3개를 Git 커밋 또는 별도 제출 자료로 확실히 연결한다. 로컬 파일 존재와 제출 완료는 다르다.
5. **발표 문구 정리:** “모바일로 불가능” 대신 “차량 통합으로 더 유용”, “실차 필수” 대신 “에뮬레이터로 입증”으로 설명한다.

### PT 전 검증 우선

1. Virtual Console 또는 공식 지원 방법으로 정차 관련 신호를 바꾸고 SDK 수신 → 앱 반응을 보여 준다. 브레이크 입력만으로 실제 정지를 보장하는지 지원 신호·조건도 확인한다.
2. 실제 NaviHelper 입력으로 적어도 한 장소의 예고 → 접근 → 통과 흐름을 재현한다. 어려우면 호출·응답 로그와 데모 신호를 구별하고 기술적 제약을 설명한다.
3. 주행 제한·화면 전환·내비 음성 중단에서 무엇이 유지되고 무엇이 멈추는지 시나리오별로 확인한다. 제한 우회를 해결책으로 삼지 않는다.
4. 실제 마이크 입력과 음성 청취가 가능한 환경에서 한영 음성 및 아이 발화 응답을 확인한다. 텍스트 입력 재현을 STT 인식 성공으로 포장하지 않는다.
5. 소수 가족을 대상으로 아이가 창밖을 찾는지, 질문이 이해되는지, 보호자 개입이 얼마나 필요한지 관찰한다. 소규모 시험을 시장 전체의 유지율 증거로 일반화하지 않는다.

| 예상 질문 | 현재 근거로 답할 수 있는 내용 |

| 휴대폰의 오디오 관광 앱과 무엇이 다른가? | 후석 아이, 관심사별 질문과 대화, 차량 내비·상태·공용 오디오 통합, 가족 기억을 중심으로 차별화 |
| 모든 길가 명소에 5분 전 예고가 가능한가? | 아님. 등록된 지원 목적지·경유지는 개별 ETA, 그 밖은 GPS 접근·통과 방식 |
| 실제 주행에서도 아이가 그냥 말하면 되는가? | 0.30에서 연결 경로는 보완했지만, 현재 입증은 정차 시연까지. 제한·비전경 상태의 지원 범위를 설명 |
| 왜 SDK를 네 개 쓰는가? | 위치·시간 → 질문 시점, 차량 상태 → 정차, TTS → 창밖 청취, STT → 후석 답변이라는 대응 관계 |
| 아이가 말하지 않거나 틀린 답을 하면? | 듣기만 해도 진행하고, 채점하지 않으며 검증된 대본으로 부드럽게 설명. 예상 밖 말의 한계도 인정 |
| AI가 코드를 만들었는데 본인이 설명 가능한가? | 상태 전이, ETA와 주변 장소 구분, 오디오 완료·중단 처리, 마이크 동의·종료, 기기 내 저장을 직접 설명할 준비 필요 |
| 서울 6곳으로 어떻게 계속 사용하는가? | 초기 고객을 좁히고 가족 장소·반복 질문의 가설을 설명. 전국 서비스나 장기 유지율이 검증됐다고 하지 않음 |
| 실제 차량 없이도 인정되는가? | 공식 안내는 에뮬레이터 검증을 인정. 구현이 아닌 목업을 실제 SDK 동작이라고 설명하지 않는 것이 중요 |
